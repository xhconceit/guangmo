# 广莫项目技术总览

## 1. 文档目的

本文件用于集中列出广莫项目当前采用、未来计划采用及仍待评估的技术，
形成一份持续更新的技术总览。

文档主要回答以下问题：

- 项目现在和未来涉及哪些技术？
- 每项技术属于什么类别，在广莫中用于解决什么问题？
- 各项技术之间如何配合？
- 哪些已经使用或配置，哪些属于计划或候选方案？

### 1.1 覆盖范围

本文涵盖：

- TypeScript Monorepo 与工程化工具；
- Next.js / React Web 前端及后端接口；
- 模型接入、AI Agent、ReAct、LangChain / LangGraph 与多 Agent；
- PostgreSQL、pgvector、Drizzle、检索与记忆；
- Supabase Auth、RLS、权限与审批；
- Google Calendar、Gmail、Notion、Google Drive 等外部连接器；
- Worker、队列、定时任务与实时通信；
- 移动端应用与浏览器扩展；
- 测试、监控、构建与部署。

### 1.2 阅读方式

各技术条目按“技术名称、类型、用途、状态”组织。

技术状态统一分为：
“已使用、已配置、计划使用、待评估、未使用”，
具体含义见第 17 节。

同一技术在不同应用或能力中的状态可能不同，应结合使用范围阅读。
尚未确认的条目可以附加“待核实”标记。

### 1.3 文档边界

- 列出某项技术，不代表已经实现或已经决定采用。
- 候选方案用于保留选择空间，不要求全部引入。
- 用途描述说明技术在广莫中的作用，不等于当前功能完成情况。
- 本文以技术清单和关系说明为主，不展开完整的实现步骤、接口设计或验收记录。
- 随项目推进，逐步补充遗漏项、确定选型，并更新技术状态。

## 2. 项目定位

广莫是一个帮助用户管理、理解与推进真实生活的个人 Agent。

它围绕对话、记忆、项目、学习安排、日程和外部信息，
帮助用户整理信息、形成判断、制定计划并推进具体行动。

本节描述产品目标与规划范围，不代表所有能力均已实现。

### 2.1 主要场景

| 场景           | 希望提供的能力                                         |
| -------------- | ------------------------------------------------------ |
| 日常对话与记录 | 接收问题、想法和零散信息，帮助用户整理与思考           |
| 个人记忆       | 保存用户确认的信息，在后续交流和任务中提供相关上下文   |
| 项目推进       | 将目标拆解为任务，整理资料、跟踪进展并提出下一步建议   |
| 学习安排       | 围绕学习目标组织计划、材料、练习和反馈                 |
| 日程管理       | 结合已有安排提出时间建议，并在授权与审批范围内执行操作 |
| 外部信息整合   | 连接邮件、日历、笔记和文件，减少跨工具查找与整理       |
| 研究与行动辅助 | 检索资料、比较方案、生成草稿，并协助完成明确授权的任务 |

### 2.2 多端定位

| 用户入口   | 主要职责                                           |
| ---------- | -------------------------------------------------- |
| Web 工作台 | 承载完整的对话、项目、记忆管理、执行结果与审批操作 |
| 移动端应用 | 支持随手记录、查看安排、接收提醒和处理审批         |
| 浏览器扩展 | 收集网页资料，将当前页面内容带入广莫的对话和项目   |

各端围绕同一用户的数据与业务能力协作，
具体技术方案和建设阶段见对应章节。

### 2.3 产品边界

- 用户保留目标选择、重要判断和操作批准的控制权。
- 系统区分用户明确提供的事实、外部资料和 Agent 推测。
- 需要审批的操作，在批准前只能准备或起草，不能直接执行。
- Agent 结果应区分建议、待执行操作和已经完成的操作。
- 多 Agent、移动端和浏览器扩展属于可逐步建设的能力，
  不作为所有核心功能的前置条件。

### 4.3 技术之间的关系

- TypeScript 负责语言与类型检查，pnpm 负责依赖和工作区管理。
- Monorepo 是仓库组织方式，不要求必须引入 Turborepo 或 Nx。
- ESLint 侧重代码检查，格式化工具侧重排版；是否组合使用取决于配置。
- 共享包可以先共享类型，再按需要共享业务规则，不要求所有端复用全部代码。
- 跨包任务工具根据工程规模引入，简单阶段可以先使用包管理器脚本。
- Changesets 适用于需要版本管理或发布的包，不是私有共享包的必需工具。

- Markdown 和富文本内容展示需要处理不可信内容，不能直接信任外部 HTML。
- 响应式 Web 可以服务移动浏览器，但不等同于独立移动端应用。

### 6.4 技术之间的关系

- Route Handlers 接收和返回 HTTP 请求，业务逻辑可以由独立模块承载。
- REST 描述接口组织方式，OpenAPI 描述接口约定，两者可以配合使用。
- Server Actions 面向 Web 内部交互，不替代移动端和扩展所需的公共接口。
- Service Layer 处理业务规则，Repository 处理数据读写，Adapter 处理外部服务差异。
- TypeScript 提供静态类型检查，运行时校验处理实际收到的数据。
- CORS 是浏览器访问控制机制，不能替代身份认证与权限检查。
- 缓存需要考虑用户隔离、权限变化及数据更新，不能只按 URL 判断是否复用。
- 耗时操作可由接口创建任务，再交给 Worker 执行；不要求一直保持原请求连接。

- 模型 API / SDK 负责调用模型，Provider Adapter 负责统一项目内部的调用方式。

### 7.3 AI 技术的选型关系

| 技术 / 方案 | 解决的问题 | 与其他方案的关系 |
| --- | --- | --- |
| 模型 API / SDK | 如何调用模型 | 是模型接入方式，不决定 Agent 架构 |

| 单 Agent Loop | 如何持续处理任务与工具结果 | 可以自行实现，也可以借助框架 |
| ReAct | 如何组织推理、行动和观察的迭代 | 是工作模式，不是框架，也不要求多 Agent |
| LangChain | 如何复用模型、工具和检索等集成 | 是候选框架，不是 Agent 的必需依赖 |
| LangGraph | 如何组织有状态的执行流程 | 可用于单 Agent 或多 Agent，不自动决定具体工作模式 |
| 多 Agent | 如何让多个 Agent 分工与协调 | 是架构选择，不等同于多次模型调用 |
| RAG | 如何让模型利用检索到的资料 | 可以用于普通问答，也可以作为 Agent 的一项能力 |

选型时分别回答：

1. 使用什么模型，以及如何接入？
2. 任务采用固定流程，还是允许 Agent 动态选择下一步？
3. 是否需要框架提供集成或状态管理？
4. 一个 Agent 是否足够，是否确有分工协作需求？
5. 回答是否需要检索个人记忆或外部资料？

这些决定相互关联，但不能相互代替。
本表仅解释选型关系，不改变各项技术的当前状态。

### 9.4 技术之间的关系

- Supabase Auth 处理身份认证与会话，RLS 和服务端权限检查负责限制数据及操作访问。
- 外部服务 OAuth 授权与广莫自身登录分别管理。
- 工具权限决定操作是否允许，审批决定用户是否同意本次具体操作。
- 模型提出工具调用请求后，仍需由应用校验并执行。
- 幂等控制处理重复执行问题，不能替代权限检查或审批。
- 沙箱执行仅在引入代码执行能力时评估，不是普通模型调用的必需组件。

### 安全原则

数据隔离：每个用户只能读取和修改自己的数据。
最小权限：只申请完成当前能力所需的最少外部权限。
人工审批：发送邮件、修改日程、更新外部文档等动作必须先给用户看。
可追溯性：用户能知道 Agent 做过什么、基于什么信息、是否真的执行成功。

### 连接器原则

用户主动授权，广莫只访问被允许的账号和范围。
每种服务独立接入；新增 Gmail 不应该改坏日历或 Agent 核心。
读取、起草和真实写入要分开；真实写入必须经过审批。

### 10.4 技术之间的关系

- Connector Adapter 封装外部服务差异，向内部工具提供清晰的操作接口。
- 连接器负责调用外部服务，Worker 和队列负责安排后台执行。
- Webhook、定时轮询和用户手动刷新是不同的同步触发方式，可以按需组合。
- 同步游标用于跟踪读取进度，不能替代写入操作的幂等控制。
- 外部内容进入记忆或检索系统后，应保留来源、所属用户和更新时间。
- 不同外部服务支持的通知、增量同步和写入能力可能不同，应分别选型。

为什么需要 Worker

一次 Agent 研究、多个连接器同步或每周回看可能很久，不能一直占着 Web 请求。
任务失败后需要重试。
用户关闭页面后，任务仍应能安全完成或停在等待审批的状态。
Worker 不能绕过权限和审批；它只是换到后台执行。

### 11.3 技术之间的关系

- Worker 执行任务，队列保存和分发待处理任务，调度器决定何时触发任务。
- Trigger.dev 与 BullMQ + Redis 是需要比较的候选方案，不预设同时采用。
- 任务平台可能已经提供重试、并发控制和执行恢复能力，应先确认覆盖范围，再决定是否自行实现。
- SSE、轮询和 WebSocket 用于客户端获取状态，不负责保存或执行后台任务。
- 任务状态机管理执行进度，审批状态机管理用户是否批准具体操作，两者需要协作。
- 等待审批通常需要保存状态并暂停后续执行，不要求 Worker 一直占用运行资源。
- 取消任务不等于撤销已经发生的外部操作；需要分别处理停止执行与操作补偿。

### 14.4 技术之间的关系

- 测试策略说明要验证什么，测试工具负责执行具体检查。
- 模拟接口用于验证可控场景，不能代替真实服务的接入测试。
- Agent 评测关注模型行为与任务结果，传统测试关注确定性的代码规则，两者需要配合。
- 日志记录事件，指标反映运行趋势，链路追踪关联跨服务执行过程。
- 业务审计记录与调试日志用途不同，应分别确定内容和保留规则。
- CI 平台执行交付流程，部署平台承载应用，Docker 是可选的打包与运行方式。
- 应用回滚不等于数据库回滚，数据库迁移需要单独考虑兼容与恢复。
- Web、Worker、移动端和浏览器扩展分别选择交付方式，不预设统一部署。

## 16. 技术选型原则

本技术总览同时收录当前技术、明确计划和候选方案。
列入清单不代表必须采用，最终选择应服务于具体业务需求。

### 16.1 基本原则

| 原则            | 在广莫中的应用                                                     |
| --------------- | ------------------------------------------------------------------ |
| 需求优先        | 先明确要解决的问题，再选择技术；不因框架流行而引入                 |
| 优先 TypeScript | 在适合的应用与服务中优先使用 TypeScript，便于共享类型与维护        |
| 先完成核心流程  | 优先建设 Web、单 Agent、数据存储、权限与审批，再按需求扩展其他能力 |
| 从简单方案开始  | 当前需求能由简单实现满足时，暂不引入额外框架或服务                 |
| 安全与用户控制  | 涉及个人数据和外部操作时，将授权、隔离、审批和撤销纳入设计         |
| 明确模块边界    | 将业务规则与模型供应商、外部服务和存储实现适度分离                 |
| 复用已有能力    | 引入新工具前，先确认现有框架或平台是否已经提供所需功能             |
| 考虑维护成本    | 同时评估开发、部署、升级、排错和长期运行的成本                     |

| 可维护性   | 文档、调试手段、升级路径和项目维护情况是否满足需要？   |
| 可迁移性   | 数据能否导出？替换技术时需要改动哪些部分？             |

- 已确认不采用且未纳入配置、计划或评估的相关技术，标为“未使用”。

## 17. 技术状态说明

本文统一使用以下五种技术状态。状态应结合明确的功能范围和核查依据判断，不能仅凭技术名称出现在文档、依赖或配置中，就认定为“已使用”。

| 状态     | 含义                                                 | 判断依据                                                           |
| -------- | ---------------------------------------------------- | ------------------------------------------------------------------ |
| 已使用   | 已在明确的功能范围内实际接入并运行                   | 实际调用或实现位置，以及运行、测试或部署验证记录                   |
| 已配置   | 已完成依赖、配置或基础设施准备，但尚未确认实际运行   | 依赖声明、配置文件、初始化代码或迁移记录；仅有占位配置不算完成配置 |
| 计划使用 | 已决定采用并纳入后续实施计划，但尚未落地             | 明确的选型决策、实施任务或路线图                                   |
| 待评估   | 尚未决定是否采用，需要比较方案或进行验证             | 候选方案、评估问题或验证任务                                       |
| 未使用   | 在当前核查范围内未采用，也未归入配置、计划或评估状态 | 对相关代码、配置和计划的检查结论                                   |

使用这些状态时，应遵循以下规则：

- 缺少证据时，标记“待核实”，不直接判断为“已使用”或“未使用”。“待核实”是核查标记，不是第六种技术状态。
- 同一技术在不同功能中的状态可以不同，应注明适用范围；相同范围的状态应在各章节保持一致。
- 已完成配置且计划继续接入时，当前状态写“已配置”，后续接入工作另行说明。
- “已使用”不代表全部能力已经完成，也不代表已经在生产环境部署；实际使用范围和验证环境应单独注明。
- ReAct、LangChain、LangGraph 和多 Agent 协作应分别核查，不能根据项目包含 AI Agent 就推定它们已经使用。

| 扩展开发       | WXT / Plasmo / 自定义构建              | 哪种方式适合目标浏览器和界面入口？         |
| 单元测试       | Vitest / Jest                          | 与现有工程配置及测试需求如何配合？         |
| Web 流程测试   | Playwright / 其他方案                  | 优先自动化哪些核心操作流程？               |
| 移动端流程测试 | Maestro / Detox / 其他方案             | 与所选移动端技术和构建流程是否兼容？       |


### 18.4 选型优先顺序

以下为建议的选型时机，不代表技术已经采用，
也不改变各条目的当前状态。

| 选型时机 | 需要确认的技术 | 决定依据 |
| --- | --- | --- |
| 开始模型接入前 | 模型供应商、SDK、结构化输出与工具调用方式 | 首个 Agent 场景需要哪些模型能力 |
| 开始核心数据功能前 | 数据库部署方式、Drizzle 接入、身份认证与 RLS 配合 | 数据结构、用户隔离和运行环境 |
| 开始 Agent 执行流程前 | 自研流程、ReAct、LangChain、LangGraph 的采用范围 | 是否需要动态决策、状态持久化、暂停与恢复 |
| 开始后台任务前 | Trigger.dev、BullMQ + Redis 或其他方案 | 任务时长、定时执行、重试及部署要求 |
| 开始资料检索前 | Embedding、文件存储、解析与分块方案 | 首期资料类型、数据规模和检索需求 |
| 开始进度展示前 | 轮询、SSE 或 WebSocket | 更新频率及是否需要双向通信 |
| 开始移动端建设前 | 移动端框架、本地存储与构建分发方案 | 设备能力、离线需求和维护成本 |
| 开始扩展建设前 | 扩展开发框架、目标浏览器与权限范围 | 网页采集和侧边栏等具体场景 |
| 出现明确需求后 | 多 Agent、本地模型、Reranking、复杂同步 | 现有方案出现了什么可验证的不足 |

基础测试、权限控制和必要日志应随功能一起建设。
监控深度、负载测试和复杂发布策略再按运行规模逐步完善。

## 19. 文档准确性与一致性检查

本节用于检查技术总览是否与项目实际情况一致，重点核对技术状态、实现范围、依赖关系及跨章节表述。

### 19.1 检查原则

1. 技术状态应有代码、配置、数据库迁移、测试结果或部署记录等依据。
2. 安装依赖、填写环境变量、创建目录，不等于功能已经实现。
3. 局部功能已经实现，不等于整条业务流程已经可用。
4. 开发环境验证通过，不等于生产环境已经部署并验证。
5. 同一技术在不同章节中的状态应保持一致；如果使用范围不同，应明确说明。
6. 缺少证据时，应标记“待核实”，不能直接判断为“已使用”或“未使用”。

“待核实”是核查标记，不是新的技术状态。

### 19.2 技术状态的核对标准

| 技术状态 | 判定标准                                             | 需要核对的依据                           | 表述示例                                     |
| -------- | ---------------------------------------------------- | ---------------------------------------- | -------------------------------------------- |
| 已使用   | 已在明确的功能范围内实际接入并运行                   | 调用代码、运行结果、测试或部署记录       | 已在【功能】中使用【技术】，并在【环境】验证 |
| 已配置   | 已完成依赖、配置或基础设施准备，但尚未确认实际运行   | 依赖声明、配置文件、初始化代码、迁移记录 | 已配置【技术】，尚未完成【功能】的运行验证   |
| 计划使用 | 已明确纳入后续实施计划，但尚未落地                   | 方案、任务或路线图                       | 计划在【阶段】使用【技术】实现【目标】       |
| 待评估   | 尚未决定是否采用，需要比较方案或进行验证             | 候选方案、评估问题、验证任务             | 待评估【技术】是否满足【需求】               |
| 未使用   | 在当前核查范围内未采用，也未归入配置、计划或评估状态 | 对相关代码、配置和计划的检查             | 当前【范围】未使用【技术】                   |

如果一项技术已经完成配置，同时计划继续接入，主状态写“已配置”，下一步写“计划完成接入”，避免在不同章节分别写成两个状态。

| 状态变化          | 更新前需要确认                                         |

| 待评估 → 计划使用 | 已决定采用，并明确用途或实施阶段                       |
| 计划使用 → 已配置 | 已存在可核查的配置或基础设施准备                       |
| 已配置 → 已使用   | 已在明确功能中实际运行，并有验证依据                   |

1. 核对代码、配置及验证记录，确定实际发生的变化。

3. 检查技术分类、依赖关系、状态说明和待确认选型等相关章节。

5. 对证据不足的内容保留“待核实”标记。

| 术语              | 本文中的含义                                               | 需要区分的边界                                   |

| 审批机制   | 在受控操作执行前校验人工批准结果的控制流程             | 应约束实际执行，不能仅表现为界面确认                          |
| 部署       | 将应用发布到目标运行环境的过程                         | 部署成功不等于业务验证、监控和恢复能力均已完成                |

### A.5 术语使用规则

1. 首次出现时使用完整名称，必要时附上缩写。
2. 同一概念在各章节中保持相同名称。
3. 将技术能力、项目实现情况和后续计划分别表述。
4. 描述“支持某项能力”时，注明支持主体是框架、外部服务还是广莫项目。
5. 技术状态统一使用“已使用、已配置、计划使用、待评估、未使用”；缺少证据时附加“待核实”标记。

## 附录 B：技术状态与证据索引

本附录汇总技术状态的核查依据。各技术章节负责说明用途和实现范围，本附录负责记录证据位置。

证据应指向实际存在的代码、配置、验证记录或计划。尚未找到依据时，填写“待核实”，不编造文件路径或验证结果。

### B.1 证据记录格式

按可以独立判断状态的技术或能力分别记录。相同技术的不同能力可以具有不同状态。

| 技术或能力         | 当前状态                             | 实现或配置依据                           | 验证或决策依据                         | 适用范围与环境     | 核查日期       |
| ------------------ | ------------------------------------ | ---------------------------------------- | -------------------------------------- | ------------------ | -------------- |
| 【技术或具体能力】 | 【五种状态之一；未确认则填“待核实”】 | 【实际文件路径、配置位置；不适用则注明】 | 【测试结果、运行记录、决策或计划位置】 | 【功能范围及环境】 | 【YYYY-MM-DD】 |

“待核实”仅表示尚未完成状态判断，不构成第六种技术状态。

### B.2 不同状态对应的证据

| 技术状态 | 应记录的主要依据                                 | 不能单独作为判断依据的内容     |
| -------- | ------------------------------------------------ | ------------------------------ |
| 已使用   | 实际调用或实现位置，以及对应运行验证             | 依赖声明、示例代码、设计方案   |
| 已配置   | 已生效的依赖、配置或基础设施准备                 | 只有占位值的配置模板、待办事项 |
| 计划使用 | 明确采用的决策、实施任务或路线图                 | 讨论中随口提及、候选技术清单   |
| 待评估   | 评估问题、候选方案及待验证事项                   | 无法确认是否采用的模糊描述     |
| 未使用   | 明确的核查范围，以及对实现、配置和计划的检查结论 | 一次关键词搜索没有结果         |

### B.3 证据记录注意事项

1. 尽量记录具体文件、符号、测试用例或任务位置，避免只填写仓库首页。
2. 运行验证应注明日期、环境和实际覆盖的能力。
3. 如需保留历史依据，可记录提交编号或构建编号。
4. 文件移动、实现替换或方案调整后，应更新相关索引。
5. 不在文档中粘贴密钥、访问令牌、用户隐私数据或完整敏感日志。
6. 同一项依据只能支持其实际覆盖的结论，不应扩大解释范围。

### B.4 填写示例

以下为假设示例，不代表广莫项目当前状态。

假设 Google Calendar 只完成了日程读取的接入验证，可以分别记录：

| 技术或能力               | 当前状态 | 依据                               | 能力边界                           |
| ------------------------ | -------- | ---------------------------------- | ---------------------------------- |
| Google Calendar 日程读取 | 已使用   | 【读取实现位置】及【运行验证记录】 | 仅覆盖已验证的读取流程             |
| Google Calendar 日程创建 | 待核实   | 尚未核查实现与计划                 | 不能根据读取能力推定创建能力的状态 |

假设 LangGraph 只出现在候选方案中，且尚未决定采用：

| 技术或能力 | 当前状态 | 依据                       | 尚待解决的问题           |
| ---------- | -------- | -------------------------- | ------------------------ |
| LangGraph  | 待评估   | 【候选方案或评估记录位置】 | 【需要验证的适用性问题】 |

不能因为文档提到 LangGraph，就将其记录为“已配置”或“已使用”。

## 附录 C：关键业务流程与实现边界

### C.1 流程记录原则

1. 每条流程应明确触发方式、主要步骤、完成条件和失败处理。

### C.3 示例：用户通过 AI 创建日程

以下仅展示待核查的流程结构，不代表项目已经实现，也不代表已经决定采用其中全部模块。

- [ ] 正常输入能够得到预期结果。

## 附录 E：阶段验收与完成标准

本附录用于定义具体能力的完成条件，避免将依赖安装、配置完成、局部运行或页面展示，直接等同于业务能力交付。

验收结论与技术状态分别记录。某项技术“已使用”，不代表依赖该技术的全部业务能力均已完成。

### E.1 验收原则

1. 验收对象应是具体能力，例如“读取当前用户的日程”，而不是笼统的“完成连接器”。
2. 开始验收前，应明确范围、环境和通过标准。
3. 验收应覆盖正常流程及与该能力相关的关键失败场景。
4. 使用模拟数据或模拟服务时，应明确说明。
5. 未验证的项目不能填写为通过。
6. 本阶段不包含的能力应单独列出，避免扩大完成范围。

### E.2 单项能力验收模板

#### 验收对象：【具体能力名称】

- 所属阶段：【填写】
- 验收范围：【本次包含的功能】
- 暂不包含：【本次不覆盖的功能】
- 验证环境：【开发／测试／生产，及必要说明】
- 关联版本：【提交编号或构建编号】
- 验收日期：【YYYY-MM-DD】

| 验收项     | 通过标准                             | 验证结果                         | 证据位置 |
| ---------- | ------------------------------------ | -------------------------------- | -------- |
| 正常流程   | 【用户能够完成的具体操作及预期结果】 | 【待验证／通过／未通过／不适用】 | 【填写】 |
| 输入处理   | 【缺失或无效输入得到明确处理】       | 【填写】                         | 【填写】 |
| 身份与权限 | 【仅允许正确用户访问对应能力和数据】 | 【填写】                         | 【填写】 |

填写“不适用”时应说明原因。范围内的必需验收项存在未通过或待验证时，不应将整项能力标记为验收通过。

### E.3 示例：审批后创建日程

以下为假设示例，仅展示验收标准，不代表项目已经实现该能力。

验收范围：用户确认日程内容后，在其已授权的 Google Calendar 中创建一条日程，并获得执行结果。

暂不包含：日程修改、删除、重复日程及其他用户的日历操作。

| 验收项     | 通过标准                                                     |
| ---------- | ------------------------------------------------------------ |
| 内容确认   | 审批前展示标题、起止时间、时区和目标日历                     |

- 对应技术章节中的状态与使用范围。
- 关键业务流程中的验证结果。
- 技术状态与证据索引中的记录。
- 当前能力边界与遗留事项。
- 文档变更记录。

验收通过的表述应包含范围和环境，例如：

“【能力】已在【环境】完成验收，覆盖【具体范围】；
【未覆盖能力】不在本次验收范围内。”

## 附录 F：待核实事项与核查闭环

本附录集中记录文档中证据不足、表述冲突或实现范围不明确的事项。

“待核实”是核查标记，不是技术状态。核查完成后，应根据事实确定为“已使用、已配置、计划使用、待评估、未使用”之一，并同步修正相关章节。

### F.1 核查事项记录

| 编号  | 所在章节 | 待核实问题                 | 当前表述           | 所需证据                                 | 核查进度                   | 核查结论         |
| ----- | -------- | -------------------------- | ------------------ | ---------------------------------------- | -------------------------- | ---------------- |
| V-001 | 【章节】 | 【一个可以明确回答的问题】 | 【原文或现有状态】 | 【需要检查的实现、配置、计划或运行记录】 | 【未开始／核查中／已关闭】 | 【未确认则留空】 |

每条记录应聚焦一个问题。不同能力应分开核查，避免用一个宽泛结论覆盖多个实现范围。

### F.2 问题拆分示例

以下为核查问题示例，不代表项目当前存在这些情况。

| 过于宽泛的问题         | 可以独立核查的问题                                                          |
| ---------------------- | --------------------------------------------------------------------------- |
| 数据库是否完成？       | 应用是否实际连接 PostgreSQL 并完成读写？                                    |
| 向量记忆是否完成？     | pgvector 是否已配置？是否完成向量写入和检索？检索结果是否实际用于业务流程？ |
| 权限是否完成？         | 登录是否验证通过？目标表是否配置 RLS？跨用户访问是否被拒绝？                |
| Agent 是否完成？       | 是否存在实际工具执行？是否根据执行结果继续处理任务？停止条件是什么？        |
| LangGraph 是否已使用？ | 是否存在实际导入和调用？对应流程是否运行验证？还是仅出现在候选方案中？      |
| 队列是否完成？         | 是否能投递和消费任务？进程重启后任务如何处理？失败重试是否验证？            |

表中同一行包含多个问题时，应在正式记录中拆成多条事项。

### F.3 核查处理步骤

1. 找到原表述及所有引用该结论的章节。
2. 明确需要判断的是技术状态、能力范围还是验证结果。
3. 检查对应证据，记录证据覆盖的版本与环境。
4. 根据证据形成结论；仍无法判断时保持事项开放。
5. 修改相关章节，并更新证据索引。
6. 确认跨章节表述一致后，关闭核查事项。

### F.4 关闭标准

核查事项满足以下条件后，可以标记为“已关闭”：

- 已得到有依据的结论。
- 已明确结论适用的功能范围和环境。
- 已修正或确认原文表述。
- 已同步检查关联章节。
- 已记录证据位置与核查日期。

“核查已关闭”只表示文档中的疑问得到解决，
不代表相关功能已经完成。

例如，确认某项技术仅属于候选方案后，
可将其状态修正为“待评估”并关闭核查事项；
后续评估工作仍可继续。

### F.5 核查优先级

优先处理以下事项：

1. 将计划或候选技术写为“已使用”的表述。
2. 关于权限隔离、审批控制和外部写入操作的完成声明。
3. 关于完整业务流程、生产部署或验收通过的声明。
4. 同一技术在不同章节出现的状态冲突。
5. 其他缺少依据或范围不清的描述。

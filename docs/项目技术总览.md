# 广莫项目技术总览

## 1. 文档目的

这份文档用于说明广莫项目整体涉及的技术，包括编程语言、前端、后端、AI Agent、数据、外部连接器、多端应用与安全方案。

## 2. 项目定位

广莫是一个帮助用户管理、理解与推进真实生活的个人 Agent。

它通过对话、记忆、项目、学习安排、日程和外部信息连接，帮助用户形成判断、制定计划并推进具体行动。

## 3. 技术分类

本项目的技术按以下类别说明：

- 编程语言与工程化
- 前端与 Web

- AI 与 Agent

- 身份、权限与安全
- 外部连接器
- 异步任务与实时通信
- 移动端应用
- 浏览器扩展
- 测试、监控与部署

### 安全原则

数据隔离：每个用户只能读取和修改自己的数据。
最小权限：只申请完成当前能力所需的最少外部权限。
人工审批：发送邮件、修改日程、更新外部文档等动作必须先给用户看。
可追溯性：用户能知道 Agent 做过什么、基于什么信息、是否真的执行成功。

| 服务 / 技术 | 类型 | 用途 | 状态 |
| -----       | ---- | ---  | ---- |

| Gmail API | 邮件连接器 | 搜索邮件、整理待办、起草并批准发送邮件 | 计划使用 |
| Notion API | 知识库连接器 | 读取和整理用户授权的页面、笔记和数据库内容 | 计划使用 |
| Google Dirve API | 文件连接器 | 搜索，读取和整理用户授权的文件 | 计划使用 |
| OAuth 2.0 | 授权协议 | 让用户安全地连接第三方账号 | 计划使用 |

### 连接器原则

用户主动授权，广莫只访问被允许的账号和范围。
每种服务独立接入；新增 Gmail 不应该改坏日历或 Agent 核心。
读取、起草和真实写入要分开；真实写入必须经过审批。

| BullMQ | 队列框架 | 管理任务队列、失败重试和并发执行 | 待评估 |
|  Redis | 队列存储 / 缓存 | 为 BullMQ 提供队列和任务状态存储 | 待评估 |

为什么需要 Worker

一次 Agent 研究、多个连接器同步或每周回看可能很久，不能一直占着 Web 请求。
任务失败后需要重试。
用户关闭页面后，任务仍应能安全完成或停在等待审批的状态。
Worker 不能绕过权限和审批；它只是换到后台执行。

## 15. 技术依赖关系

```text
前端 Web / 移动端 / 浏览器扩展
              │
              ▼
        统一 API 与身份认证
              │
              ▼
数据库、权限、审计与记忆
              │
              ▼
单 Agent、工具调用与审批机制
          ┌───┼───┐
          ▼   ▼   ▼
     外部连接器  后台任务  多 Agent 协作
```

用户入口层：Web、移动端、扩展都是用户使用广莫的入口。
基础服务层：它们都要共用 API、登录、数据库和权限。
Agent 安全层：Agent 要先有记忆、工具权限和审批，才有资格接触外部服务。
扩展能力层：连接器、后台任务、多 Agent 都建立在前面三层稳定后。


## 16. 技术选型原则

- 项目统一优先使用 TypeScript，减少不同端之间的沟通和维护成本。
- 项目、记忆、审批等核心业务规则应与具体框架、数据库和模型供应商解耦。
- 用户数据安全优先：默认隔离数据、最小化授权、加密保存凭证，并保留审计记录。
- 用户始终拥有控制权：Agent 可以研究、建议和起草，但外部操作与长期记忆必须允许用户确认、修改或拒绝。
- 先完成安全可靠的单 Agent 闭环，再扩展多 Agent、复杂连接器、移动端和浏览器扩展。
- 模型、队列、部署等基础设施通过适配层组织，以便后续替换和维护。

广莫的技术建设不以堆叠框架为目标，而是以安全、可控地帮助用户推进真实生活为目标。

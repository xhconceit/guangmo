# 广莫 MVP 技术方案

## 0. 技术决策

广莫从第一天使用 TypeScript Monorepo。

原因不是要提前拆微服务，而是个人 Agent 必然会长出多个端：Web 工作台、后台 Agent Worker、未来移动端和浏览器扩展。核心的 Agent、记忆、权限、数据模型和连接器必须共享。

MVP 只有两个部署单元：

1. Web App：用户界面、登录、同步请求；
2. Worker：异步 Agent 任务、定时回看、连接器同步。

## 1. 技术选型


| 范围 | 选择 | 为什么 |
|---|---|---|
| 语言 | TypeScript | 前端、后端、Agent 和 Worker 共用一种语言 |
| Monorepo | pnpm workspace + Turborepo | 共享包、统一类型、独立构建与缓存 |
| Web | Next.js + React | 对话、项目、记忆、审批界面 |
| Web API | Next.js Route Handlers | MVP 不再单独维护一套 HTTP 服务 |
| Worker | Node.js + TypeScript | 长任务、重试、定时任务不能占用 Web 请求 |
| 数据库 | PostgreSQL | 强事务、结构化个人数据、审计记录 |
| 语义搜索 | pgvector | 个人笔记和记忆检索先与 PostgreSQL 放在一起 |
| ORM | Drizzle ORM | SQL 可控、类型推导清晰、迁移轻量 |
| 身份 | Supabase Auth | 登录、OAuth、数据库用户身份 |
| 授权 | PostgreSQL RLS + 服务端权限检查 | 个人数据必须默认隔离 |
| 文件 | Supabase Storage 或 S3 | 笔记附件、导入文档 |
| 日程 | Google Calendar API | 第一个外部连接器 |
| 任务队列 | Trigger.dev 或 BullMQ + Redis | 异步执行、定时、重试 |
| 模型 | Provider Adapter | 业务代码不直接依赖某一家模型 API |

## 3. 每个模块负责什么


### apps/web

面向用户，不能直接持有模型 Provider、Google OAuth 刷新令牌或数据库管理员密钥。

负责：

- 登录与会话；
- 对话界面；
- 今天、项目、记忆、审批页面；
- 发起同步 API 请求；
- 显示 Agent 计划、执行状态与来源；
- 让用户编辑、确认或删除记忆。

不负责：

- 长时间模型执行；
- 后台轮询日历；
- 未经审批的外部操作；
- 业务判断逻辑。

### apps/worker

一个独立 Node 进程，消费队列和定时任务。

负责：

- 执行超过 HTTP 请求时限的 Agent Run；
- 日历同步；
- 每周回看草稿；
- Agent 失败后的重试；
- 向 Web 写入可恢复的执行状态；
- 在需要用户确认时停止，不继续外部操作。

### packages/domain

不依赖 Next.js、数据库或模型 SDK。

这里定义广莫真正的业务语言：

- Direction：用户确认的发展方向；
- Project：用户推进的项目；
- DevelopmentLine：一个问题发展成学习、行动和新选择的路径；
- Memory：事实、偏好、观察、关系、限制；
- Observation：Agent 的推测，必须可确认或拒绝；
- AgentRun：一次 Agent 工作；
- Approval：需要用户批准的外部动作。

所有其他模块使用这些类型，禁止各自发明状态名称。



### packages/db

负责数据库 schema、SQL migration 与 repository。

Repository 只做数据读写，不调用模型、不调用日历、不作发展判断。

核心 repository：

- userRepository；
- memoryRepository；
- directionRepository；
- projectRepository；
- conversationRepository；
- agentRunRepository；
- approvalRepository；
- connectorRepository；
- auditLogRepository。


### packages/agent

负责 Agent 的运行循环，不直接知道界面细节。

核心职责：

1. 解释用户意图；
2. 根据权限检索上下文；
3. 选择工具；
4. 生成短计划；
5. 执行允许的工具；
6. 遇到副作用时创建 Approval；
7. 生成结果、依据和后续选项；
8. 将记忆提议交给 memory 包处理。

Agent 由一个主循环构成，不在 MVP 里使用多 Agent。



### packages/tools

每个工具都有统一接口：

    name
    description
    input schema
    required permission
    side effect level
    execute()


MVP 工具：

- searchWeb：研究公开网页；
- getCalendarEvents：读取授权日历；
- draftCalendarEvent：生成待审批日历草稿；
- searchMemory：检索用户确认的记忆；
- createProjectDraft：创建草稿项目；
- draftDocument：起草笔记或文档；
- createReminderDraft：创建提醒草稿。


工具声明副作用级别：

- read：直接运行；
- draft：直接运行，但标记草稿；
- write_external：必须 Approval；
- destructive：必须 Approval 且二次确认。


### packages/connectors

每一种外部服务独立实现。

MVP 只有 Google Calendar Connector：

- OAuth 授权；
- token 加密存储；
- 增量同步；
- 只读事件；
- 创建事件时返回草稿，不直接提交。

后续 Notion、Gmail、Google Drive 不应污染 Agent 主循环，只新增 Connector 和 Tool Adapter。

### packages/memory

这是广莫与普通聊天产品的重要差异。

负责：

- 从对话和连接器数据中提取候选记忆；
- 给记忆分为事实、偏好、方向、观察和限制；
- 维护来源与时间；
- 提供混合检索：结构化筛选 + 全文检索 + 向量相似度；
- 将 Agent 推测保存为 observation，不自动升级为用户长期事实；
- 支持用户查看、确认、拒绝、编辑、忘记和导出。

## 5. 实际调用链

用户在 Web 输入：

    我不知道该不该接这个工作。

执行过程：

1. Web 创建 message，调用 POST /api/conversations/:id/runs；
2. API 创建 agent_run，推送 job 到 Worker，立即返回 run_id；
3. Worker 检索相关项目、用户方向、已授权日历和最近对话；
4. Agent 生成短计划，例如读取冲突日程、查明工作内容、列出取舍；
5. Tool Executor 执行所有 read 与 draft 工具；
6. Worker 写入 agent_steps，Web 用轮询或 SSE 显示过程；
7. 如果要接受会议、发邮件或修改日程，Worker 创建 approval 并将 run 设为 waiting_approval；
8. 用户批准后，Worker 恢复同一个 run；
9. Agent 返回结论：依据、选项、代价和下一步；
10. 可能的记忆以 proposed 状态显示，等待用户确认。

## 7. 权限与安全

### 数据隔离

- 浏览器只使用用户会话；
- 数据库对所有个人表启用 RLS；
- 服务管理员密钥只存在 Worker 环境；
- 每个用户查询按 user_id 强制过滤；
- RLS 测试覆盖读取、插入、更新、删除和跨用户拒绝。

### Agent 安全

- 网页内容是非可信输入，不可改变 Agent 权限；
- 每个工具有最小 scope；
- Agent 无权自行增加 Connector；
- 所有外部写操作通过 Approval；
- 工具调用、批准与失败都写入 audit_logs；
- 用户可导出和删除个人数据。


## 8. 开发顺序

### Sprint 1：基础骨架

- pnpm Monorepo；
- apps/web；
- packages/domain 与 packages/db；
- Supabase Auth、PostgreSQL、RLS；
- 用户、对话、消息表；
- 简单聊天页面。

### Sprint 2：Agent 与记忆

- packages/agent 与 packages/tools；
- 网页研究工具；
- memories 表、候选记忆与确认界面；
- Agent Run 与步骤展示。


### Sprint 3：项目和方向

- directions、projects、development_lines；
- 项目页；
- 对话中检索方向与项目；
- 发展建议以 observation 显示。


### Sprint 4：日历和审批

- Google OAuth；
- Calendar Connector；
- Approval 状态机；
- 日历事件草稿；
- Worker 队列和可恢复执行。



### Sprint 5：低频主动性

- 每周回看草稿；
- 用户自选提醒频率；
- 项目停滞或日程冲突提示；
- 不自动发送、不自动改日程。

## 9. MVP 完成定义

用户可以：

1. 登录；
2. 建立一个发展方向；
3. 输入一个现实问题；
4. 让广莫使用已确认的记忆和项目进行研究；
5. 看到 Agent 的依据、计划和建议；
6. 批准一条日历事件草稿；
7. 查看、修正或删除广莫记住的任何内容。

这套闭环跑通前，不增加移动端、多 Agent、Gmail 或浏览器扩展。
